F-7 verification — preview is reached by redirect, and refresh is no longer a 405

Branch fix/frontend-audit-2026-09-28 @ f042d17. Server :8148 (own php -S against
.scratch-uma/fe-fix.sqlite; the audit's :8144 was left running and untouched).
This finding is about HTTP behavior, so no viewport applies.

--- 1. The POST now redirects instead of rendering a body ---

POST /training-runs/1/turns  (stage=preview, turn=3, speed 560 vs stored turn 2)

    HTTP/1.1 302 Found
    Location: http://127.0.0.1:8148/training-runs/1

Before the fix the same request returned 200 with a full HTML body while the
address bar held /training-runs/1/turns. That is what made the page
un-refreshable: F5 re-issued a POST at the turns endpoint and the browser showed
405 Method Not Allowed. The redirect target is a GET-able route, so the address
bar now holds a URL that answers GET.

--- 2. The redirect target answers a plain GET ---

    GET /training-runs/1  ->  200

No 405 is reachable from the previewed state.

--- 3. The preview content survives the round trip ---

Asserted by tests/Feature/FrontendAuditFixesTest.php >>
"it reaches a preview by redirect, so refreshing it is not a 405 (F-7)", which
holds all three requirements together:

  - the POST returns a redirect to runs.show;
  - the preview wrote no row (turn count still 1);
  - the following GET renders the computed bubble "+40 Speed", so the preview is
    recomputed from the flashed input inside showData() and the redirect cost the
    screen nothing.

Recorded honestly: step 3 is proven through the test harness, not through this
curl transcript. A curl session could not be made to carry the flashed input
across the redirect -- Laravel flashes input for exactly one request and the
session-cookie handoff in a shell script is unreliable -- so the bubbles do not
appear in a curl dump of the redirected page. That is a limitation of the capture
method, not a behavioral difference: the same showData() path serves both, and the
automated test is the authoritative evidence.

--- 4. Known consequence of PRG ---

Because flashed input lives for one request, refreshing the previewed screen a
second time returns the plain run view rather than a stale preview: the Trainer
sees their logged turns instead of a 405, and previewing again is one click.
Standard PRG behavior, stated rather than left to be discovered.

--- 5. Frozen-test collision ---

8 tests in three frozen Phase 3A/3B files now fail: GuidedFirstTurnTest (3),
GuidedTurnOnRunViewTest (3), GuidedTurnStagesTest (2). Every one fails on the same
line shape -- post(...)->assertOk() where the response is now 302. They pin the
pre-PRG status code; the invariant each actually protects ("a preview writes no
rows") still holds and still passes on the assertion beneath it. Not edited, per
the frozen-test rule. Escalated in RESOLUTIONS.md.
