Annotation key · Trainee selection

  1. Cards carry the knowing, not the browsing cost. Each card shows the three aptitude axes that decide a race: surface, distance, running style. That is Miller's Law chunking — nine letters per trainee collapsed into three readable rows, with the strongest value in bold.
  2. A selection echo before the commit. The "Selected" card repeats the choice in one sentence, because a grid of twelve is easy to click past (Paradox of the Active User).
  3. Filters are one row, sort is in the row. Five controls, all inline, no filter drawer. The running screen already exposes exactly these facets (facets and sortKeys in the payload).
  4. Pagination states the denominator. "71 trainees · page 1 of 12" — the running screen prints the page but not the roster size.
  5. Released status is a word, not a colour. The pill says "Released (Global)"; the catalog's JapanOnly row is the case DESIGN.md §2.1 records as still unimplemented and is not invented here.
  6. Chosen card uses three signals — radio, 2px pick border, tint — matching the scenario step so the selection pattern is learned once (Jakob's Law).
  7. Heuristic coverage. H6. The roster shows each trainee as a recognisable card with name and aptitude letters, so the Trainer picks from what is visible instead of recalling a name to search for.
  8. Framework coverage. Gerhardt-Powals 1 on automating unwanted workload. The roster is a search over a catalogue rather than a free-text field, because the product already owns the data and the Trainer should not have to type a name to find it.

Wireframe only. Admire Vega's name, slug, form, rarity and full aptitude set are the live payload's; Agnes Digital and Rice Shower are shown to demonstrate density and their aptitude figures are illustrative. Real records: /career/setup/trainee, read 2026-10-21.
