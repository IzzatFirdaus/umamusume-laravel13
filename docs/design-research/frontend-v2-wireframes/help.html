How this works

The screen is meant to be usable without this page. This page exists for the two cases where it is not: a rule that is easier to look up than to infer, and a state that needs diagnosing.

The turn loop

One turn, one committed action. Everything else is a record of it.

  1. Open the cockpit. Turn, Energy, Mood and the next obligation are in the first viewport.
  2. Pick this turn's action on Training, Races or Events.
  3. Record the outcome. The turn is written only after the action resolves.
  4. The timeline keeps every turn with its deltas, so the run can be read back.

○ Undo. A committed turn is reversible from the screen it was committed on, through Undo last turn. This is the one control the shipped build does not have, and it is recorded as a gap rather than drawn as if it worked.

What the tags mean

Only exceptions are marked. An unmarked figure is confirmed.

∑CalculatedThe tool derived it from values you entered. The rule is stated beside it.
~EstimatedAn approximate figure, or one resting on a single source.
?UnknownNot recorded, or not published. It is not a zero.

○ "Absence is a normal result." A field the importer cannot find stays empty. Nothing is filled with a default, because a default is an invention wearing a number.

Where the numbers come from

Rules that are easier to look up

Energy50 is the sourced advisory line. Below it the failure curve changes character rather than degrading evenly.
MoodFive tiers. GREAT +20%, GOOD +10%, NORMAL 0, BAD −10%, AWFUL −20% on training yield.
SparksBlue is the stat spark, Pink the aptitude spark. The cap raise is a separate mechanic.
Bond0 to 100. A card turns orange at 80, which is where Friendship Training becomes available.
DeckSix slots. Two copies of one card cannot be equipped together.

○ Each row is a link target in a built product. Here they are text, because this is a static wireframe and a link that goes nowhere would be the defect D-81 names.

If something looks wrong

A figure is marked UnknownThe tool was never told it. The import preview shows which fields a parse could not find.
A race is not selectableIts row states the gate. Races keeps blocked rows visible for that reason.
The turn count disagreesAn import records a position, not a history. The preview states the consequence before the commit.

Still wrong? Check the source before assuming the tool is right.

Annotation key · Help

  1. This page is the H10 gap closed. Nielsen's tenth heuristic allows documentation where it is needed, and requires it to be searchable, task-focused, concrete and not too large. Four sections, each answering a question a Trainer arrives with, is the smallest shape that meets that.
  2. Proactive help leads, reactive follows. The turn loop is the help a first-run Trainer needs; the two lower cards are the lookup a returning one needs. NN/g's split, applied in that order because proactive help is read once and reactive help is read repeatedly.
  3. It is reachable from every screen but absent from the rail. The rail already carries ten destinations, and adding an eleventh to hold a page that is not part of the run would spend navigation on something used rarely. The top bar's ? is the entry, which is also what makes it discoverable.
  4. Undo is described, not drawn. The shipped build has no undo after a committed turn. Describing it here and marking it as a gap is honest; a button that did nothing would be the D-81 defect.
  5. No link that goes nowhere. The rule rows are text rather than links because there are no target pages behind them in this set. An inert control that looks live is a defect; a sentence that says what it would link to is not.
  6. Framework coverage. WCAG 3.2.6 on consistent help and Shneiderman 2 on universal usability. The entry is in the same place on every page, and the content is written for the novice and the expert at once, with the keyboard contract stated rather than assumed.
  8. The rail collapses, and the word never leaves the DOM. The app can collapse its global navigation to marks instead of words, and this set does the same (AppLayout.vue:191-233). A collapsed destination moves its label to sr-only and gains a title, so it keeps its accessible name; the active one keeps aria-current="page" and a left rule, so state never rides on colour alone. The control is in the top bar because the bar is the one row present at every width. The choice is localStorage, not a Preference row, because Preference::KEYS is exactly theme and failure_estimate.

Wireframe only. The keyboard contract, the tag vocabulary and the rules are sourced; the screen itself is a proposal.
