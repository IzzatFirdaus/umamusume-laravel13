## Intent

Restore the NativePHP Windows pipeline by fixing the first recorded failure: the G-62 backdrop verifier cannot import NumPy in either Windows gate job. Then prove the gates do real work, build one Windows x64 installer, and have packaged acceptance install and test that exact installer. Validate the installer and updater files before they can be published. A successful ordinary branch run must not publish a release.

This is an execution guide, not a delivery record. It covers the non-vacuous gate work of S0.2/N4.8 and the CI prerequisite of S4.4. N4.9 audit and N4.10 tag decisions retain their existing authority. No app feature, runner migration, dependency upgrade, gate exemption, tag, or release is authorized by this plan. Future implementation may push a verified repair only through the brief's branch and permission rules. No push, tag, or release action belongs to this planning pass.

## Execution slices

### WCI-1: Repair the first gate in both Windows jobs

**Depends on:** the failed-attempt baseline above. **Files:** the two Windows workflow files; proposed new tools/requirements-backdrop.txt for the verifier's existing Python dependencies. `tools/verify-backdrop.py`, `resources/css/app.css` and the backdrop assets are inputs, not patch targets.

1. In a disposable tracked checkout of the failed SHA under a session-private `.scratch-uma/` directory, run `python tools/verify-backdrop.py` with a fresh CPython 3.12 x64 environment on Windows. Use `py -3.12 -m venv <session-venv>` and activate it in the Bash shell used for gates. Record `sys.executable`, Python version, missing import and exit. Keep dependencies isolated from the shared tree and the host interpreter. A clean environment reproducing the import error is useful even if an already provisioned global interpreter runs it successfully.
   Measured on this host: `py -3.12 -E -s tools/verify-backdrop.py` reproduces the CI failure exactly (`:20`, `import numpy as np`, `ModuleNotFoundError`, exit 1), and the same script under the interpreter that already carries both dependencies returns exit 0 with all six plates `ok`. So the images and the G-62 math are sound; the defect is purely provisioning. Do not treat an inherited `PYTHONPATH` as evidence about a target interpreter: on this host the ambient `PYTHONPATH` points at a 3.14 site-packages, which made `python -m pip`-free `py -3.12` load a cp314 NumPy build and fail with `No module named 'numpy._core._multiarray_umath'` — a wrong-architecture artifact, not a real 3.12 finding. Always probe the candidate interpreter isolated (`-E -s` or a venv) before recording what it holds.
2. Declare compatible, exact NumPy and Pillow versions with Windows CPython 3.12 wheels that decode the committed WebPs. Confirm that approval under `AGENTS.md` §5 covers these existing verifier imports before adding the manifest; do not change Composer or npm dependencies. After `actions/setup-python@v6`, install the same requirements in both `gates` jobs via `python -m pip install --only-binary=:all: -r tools/requirements-backdrop.txt`. Use the Python on the gate's Bash `PATH`, not bare `pip`. No cache or shared workflow abstraction needed. See [GitHub's Python dependency setup](https://docs.github.com/en/actions/automating-builds-and-tests/building-and-testing-python#installing-dependencies).
3. In the resulting environment run `python -m pip check`, `python -c "import sys, numpy; from PIL import Image, features; print(sys.executable); assert features.check('webp')"`, then `python tools/verify-backdrop.py`. Run the original full fast-gate command after the focused check. Record any new failure verbatim before investigating it.

**Accept:** the same Python installs and imports both dependencies, then all six files listed by `FILES` report `ok` with exit 0. Already measured locally on a provisioned interpreter: six `ok` lines, exit 0. Prove the same in a clean 3.12 environment, then repeat in both gate jobs at WCI-6. No changes to G-62 math, tolerances or its failure behavior. Do not proceed to packaging diagnosis while this gate is red.

Never use `pint --dirty`, blanket format the shared checkout, or treat an unknown option as a working gate. See [Pint's style test documentation](https://laravel.com/docs/13.x/pint#testing-style).
- Keep Build's gate before packaging for push, manual dispatch and reusable calls. Use the [event payload semantics](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#workflow_run) and [reusable workflow rules](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows) to tabulate trigger, actual workflow ref, checkout ref, predecessor and job condition. Do not add an independent tag build or broaden trusted input refs.

**Accept:** `bash -n tools/gates.sh` and unsuppressed `actionlint` pass. On a clean isolated candidate, `bash tools/gates.sh --fast --whole-tree-pint` logs a real Pint result, not the no-files message; normal mode keeps its scoped selection and `--fast` omits only the PHP suite. Demonstrate a real Pint failure with one temporary in-scope style violation in a disposable checkout, then remove it and rerun. Keep the negative fixture local; do not push red code to demonstrate failure. Check the job paths for failed producer, successful producer, failed Acceptance gate and successful reusable call. A skip after upstream failure is expected control flow, not passing acceptance.

2. On a suitable Windows x64 host with PHP 8.5, Node 24 and NSIS, mirror the Build job in an isolated checkout: install root dependencies from the locks, use a throwaway production-like configuration and key there, run `npm run build` and `composer run pre-native-build --no-interaction`, then run `npm ci` and `npm run plugin:build` from `nativephp/electron`.    The locked `BuildCommand` runs the bundler through `Process::...->run(...)` with no `->throw()` and no `mustRun()`, and `Illuminate\Process\PendingProcess::run()` returns a `ProcessResult` without failing on a nonzero exit. A green `native:build` step therefore does not prove electron-builder succeeded. Require the upload step to depend on the dist inventory it expects, and prove the failure path with one deliberate bundler failure that must turn the step red before any fixture is removed.
3. Verify effective app version, updater enabled/provider and intended repo/channel. If needed, pass the confirmed non-secret feed settings to the build without granting release-write access. Treat required but unavailable signing or private-feed credentials as blockers, not permission to change secrets or policies.

Expect both files even with publishing off: in `app-builder-lib` 26.8.1, `getPublishConfigsForUpdateInfo` falls back to repository inference when no publish config is supplied and generates update info "regardless of publish state", and `PublishManager` writes `app-update.yml` into the packaged resources directory on that same fallback. So an absent `latest.yml` is a finding about inference, not evidence that publishing was disabled. Also inspect the packaged `resources/app-update.yml` and confirm the owner, repo and channel it names. With the already locked YAML parser in the Electron install, require the expected `version` and the `files` entry for the installer. Resolve its URL to the exact intended GitHub asset name, accounting for the builder's safe name handling. Require matching `sha512` (base64 of the installer bytes); check size and legacy `path`/`sha512` fields when present. See the [locked Electron Builder feed generator](https://unpkg.com/app-builder-lib@26.8.1/out/publish/updateInfoBuilder.js) and [locked NSIS updater](https://unpkg.com/electron-updater@6.8.3/out/NsisUpdater.js). Use a positive fixture and missing-file, wrong-version and wrong-hash cases to check validation without a live release.

### WCI-4: Install and accept the exact artifact; check release inputs

**Depends on:** WCI-3's artifact contract. **Files:** `.github/workflows/nativephp-windows-acceptance.yml`, `.github/workflows/release.yml`; `playwright.nativephp.config.ts` and `tests/browser/nativephp-packaged.spec.ts` are existing checks. Change the spec only for a reproduced deficiency.

- **Independent:** use triggering `workflow_run.id` and `workflow_run.head_sha` with `actions: read` and `github.token` to retrieve the named artifact from the successful same-repo Build. **Reusable:** use `github.run_id`, the caller SHA, and the named same-run download after the caller's Build job. Validate the manifest and file hashes against the expected producer. Distinguish reruns by recording the producer attempt and artifact ID, not run ID or SHA alone. Never obtain the latest artifact by branch. [Download-artifact v4 inputs](https://github.com/actions/download-artifact/blob/v4/action.yml) distinguish these two paths.
- Run silent NSIS install (`/S`) of the verified setup file on a clean Windows profile.
