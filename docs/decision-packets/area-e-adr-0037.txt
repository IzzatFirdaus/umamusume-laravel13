- **Schema**: `source_key` is the entity discriminator on `match_candidates`; `NOT NULL` on every row; **architecture remains operative**; unchanged
- **Data**: 304 rows, all `gametora-races`; no second entity kind co-inhabits the table today; **unchanged**

## Recommended Ruling (Corrected)
**Accept the gap as intentionally future work (Option A)**: ADR-0037 is accepted with `source_key` as the entity discriminator; the review surfaces (race queue) already exist; the "resolve path with race semantics" gap is intentionally left for future design and is not addressed by this ADR; **the resolution lifecycle deferral is not an existing owner ruling**.

**Concrete alternatives for the resolution lifecycle (for future design, not current ruling)**:

1. **Match to an existing record** — when a Trainer reviews a race candidate, the system can match the payload to an existing `race_catalog_slots` row by `source_key` + race parameters; if a match exists, the candidate is recorded as resolved against that slot; if no match exists, the candidate remains unresolved and is presented for manual creation; **affected implementation**: `app/Http/Controllers/ReviewController.php` (review queue); `app/Models/MatchCandidate.php` (candidate model); **responsible expert**: Fullstack Expert

2. **Create a verified catalogue record** — a new resolve screen can create a fresh `race_catalog_slots` row with verified provenance: the payload's `source_key`, `proposed_name`, `course`, `direction`, `season`, `entries`, `factor effects`, and `track bias` are stored; the turn and placement are recorded from the candidate's data; **this requires a new migration, model, and controller, but is a well-scoped design question for a future ADR**; **affected implementation**: new migration/model/controller; **responsible expert**: Fullstack Expert (future ADR)

3. **Dismiss an unsupported candidate** — if the candidate cannot be matched to an existing slot and the Trainer chooses to dismiss it, the candidate row in `match_candidates` is simply marked as dismissed; **no new catalogue record is created**; the dismissal is recorded with a timestamp and the reviewer's ID; **this preserves resolution history without adding unsupported data**; **affected implementation**: `app/Models/MatchCandidate.php`; **responsible expert**: Fullstack Expert

4. **Preserve resolution history and provenance** — a future ADR can author a resolution lifecycle that records which candidates were matched, which were created, which were dismissed, and by whom; **provenance data** (source_url, snapshot_path, fetched_at, source_timezone) is already captured on `match_candidates` payload and can be leveraged; **the review queue already prints `source_key` and `proposed_name`** — a future design can build on this existing foundation; **affected implementation**: future ADR; **responsible expert**: Future Fullstack Expert

5. **Maintain review-only functionality** — the existing review queue renders race candidates with `source_key` and `proposed_name`; **this functionality is preserved and extended**: candidates can be matched to existing slots, dismissed, or flagged for future create; **no new catalogue write is required for the review-only path**; **affected implementation**: `app/Http/Controllers/ReviewController.php`; `app/Models/MatchCandidate.php`; **responsible expert**: Fullstack Expert

**Affected implementation**: `app/Http/Controllers/ReviewController.php` (review queue); `app/Models/MatchCandidate.php` (candidate model); `app/Http/Controllers/ResolveMatchCandidate.php` (resolve path, currently limited); `database/migrations/` (any new schema for resolution lifecycle)

**Responsible Backend Expert**: Fullstack Expert — the resolution lifecycle is a future design question for the Fullstack team; the accepted ADR-0037 does not close this gap; the source_key entity-discriminator architecture remains operative regardless

**Uncertainty**: Exact design of the resolve path; not needed for current ruling; the deferral is not an owner ruling
